# Student Self-Registration — Implementation and Deployment Guide

## Scope and non-goals

This release adds student-initiated account creation using single-use school invitation codes. No counsellor, teacher, school administrator, or other role can create a student account through an API/UI flow. Invitation codes are generated by an operator from the command line and distributed privately; generating an invite is not registering a student on their behalf.

Registration creates only a `users` row with role `student`, a registration audit event, and redemption of the invitation. It does **not** create a wellbeing case, case action, guardian account/link, consent record, notification, or n8n event. Existing journal/chat safety assessment and case-creation behavior remains unchanged. Existing wellbeing endpoints continue to enforce the current consent requirements.

## Design

- Public endpoint: `POST /api/auth/student/register`.
- Inputs: school tenant slug, single-use invitation code, name, school email, password, age band, and optional standard/class.
- Invite storage: `student_registration_invites`; only SHA-256 code digests are stored. Codes expire and can be redeemed once.
- Password storage: existing Argon2 password hashing.
- Account role: hard-coded to `student` on the server. The client cannot choose a role or tenant ID.
- Tenant boundary: tenant is resolved by active school slug; RLS tenant context is set before reading/writing tenant-scoped rows.
- Rate limit: per-process registration attempts are limited to 8 per IP per 15 minutes. Put a reverse-proxy/WAF rate limit in front of multi-worker or public deployments because in-memory limits are not shared across workers.
- Audit: `student_self_registered` event contains the invite ID, not password or invite code.
- No email verification is implemented in this MVP. Invitation codes must be high-entropy, single-use, and distributed privately to the intended students. For real deployment with minors, complete the school's identity-verification, privacy, guardian-consent, and legal review before using real student data. A shared public code is not acceptable; do not use one.

## Files changed

- `app/models.py`: `StudentRegistrationInvite` table model.
- `app/db.py`: add invitation table to tenant RLS enforcement.
- `app/main.py`: request validation, per-IP rate limiting, single-use invite redemption, student creation and audit.
- `app/static/index.html`, `app/static/app.js`, `app/static/styles.css`: student registration form and sign-in toggle.
- `scripts/create-student-invites.py`: operator CLI to issue codes (only digests persisted).

## Deployment prerequisites

- Windows PowerShell for the included native Windows scripts.
- Python 3.12 and PostgreSQL 16+ as described in the main README.
- Existing Saathi `.env`, database, and n8n configuration.
- A tested database backup and a separate extracted release folder.

## Safe upgrade procedure (Windows)

### 1. Back up first

1. Stop Saathi with `Ctrl+C` in the terminal running Uvicorn.
2. Open PowerShell in the current project folder.
3. Run the existing backup script and follow its prompts:

   ```powershell
   .\scripts\backup-local.ps1
   ```

4. Confirm the backup file exists and is non-empty. Keep a copy outside the project folder. Do not continue if backup failed.
5. Make a separate copy of the existing `.env` and store it securely. It contains secrets; do not email it or commit it.

### 2. Extract the release without overwriting the current folder

1. Extract the supplied `saathi-wellness-student-self-registration.zip` into a new directory, for example `C:\Saathi\saathi-wellness-mvp-registration`.
2. Copy the current project's `.env` into the new release folder. Do not replace the existing `.env` with `.env.example`.
3. Do not run `scripts\setup-local-db.ps1` against the existing database; it is for first-time local database setup and is not a migration tool.
4. If a Python virtual environment is not present in the new folder, open PowerShell there and run:

   ```powershell
   .\scripts\setup-local.ps1
   ```

   This installs the release dependencies and preserves an existing `.env`. If the environment already exists, run this command to install/verify dependencies; it does not reset the database.

### 3. Start the updated app and let the additive schema migration run

1. Ensure PostgreSQL is running and the copied `.env` points to the intended existing database.
2. Run:

   ```powershell
   .\scripts\run-local.ps1
   ```

3. Wait for `Application startup complete`. Startup's `Base.metadata.create_all` creates the new invitation table if missing, and the existing startup routine applies tenant row-level security policies including to the new table. It does not delete existing students, cases, consent records, or action history.
4. In a second PowerShell window, check:

   ```powershell
   Invoke-RestMethod http://127.0.0.1:8000/healthz
   ```

5. Open `http://127.0.0.1:8000` and confirm the existing sign-in screen loads and existing demo accounts still sign in in development mode.

### 4. Create one-time student invitation codes

Run from the new release folder after the app has started successfully (so the table exists):

```powershell
.\.venv\Scripts\python.exe .\scripts\create-student-invites.py --tenant demo-school --count 10 --expires-days 30
```

- Replace `demo-school` with the exact active tenant slug for the school.
- `--count` can be 1–500; `--expires-days` can be 1–180.
- The script prints each code once in two columns: `INVITATION_ID` and `INVITATION_CODE`. Enter only the second column (`INVITATION_CODE`) in the registration form; the UUID in the first column is an internal database ID and is not the code. The database stores only the code SHA-256 digest.
- Distribute each code privately to its intended student. Do not post codes in a shared class group, public website, source repository, or n8n payload. Treat the printed output as a secret and securely remove it from terminal transcripts/log captures if your environment records them.
- Do not reuse codes. A code is single-use and expires.

For a real school, the operator distributing codes must follow the school's approved identity-verification process. This CLI does not verify the recipient's identity or send email.

### 5. Test the new student flow

1. Sign out and select **Create a student account**.
2. Enter the tenant slug and a valid invitation code, student's own name and school email, age band, optional standard/class, and a password of at least 10 characters.
3. Confirm the account is created and the page returns to sign-in with a success message.
4. Sign in with the new account.
5. Open Privacy & Consent. Confirm the existing consent gates still apply; do not assume registration implies consent.
6. Before consent is effective, attempt a wellbeing action and confirm existing API protections still block it as designed.
7. Complete only the approved consent/assent test process in a synthetic-data environment. Initiate a support request through the existing student-facing flow and confirm that the resulting case is linked to the newly registered student.
8. Sign in as the counsellor and verify that the case shows the correct student identity/class according to existing permissions. Verify assigned teacher visibility only after the counsellor assigns the case.
9. Confirm that simply registering and signing in creates **zero** support cases and sends no registration notification/n8n event.

### 6. Negative and regression checks

- Attempt to reuse a redeemed invitation: must fail.
- Attempt an expired or random invitation: must fail with a generic message.
- Attempt registration with an existing email in the same tenant: must not create a duplicate account.
- Attempt registration against an inactive/nonexistent tenant: must fail without disclosing tenant existence.
- Submit a role or tenant ID in extra JSON fields: Pydantic ignores unknown fields by default, and the server still assigns only the active tenant resolved from the validated school slug and hard-codes role `student`.
- Make repeated failed attempts from the same IP: after the configured limit, receive HTTP 429.
- Check the audit log for `student_self_registered`; confirm it contains no password, invitation code, or wellbeing text.
- Verify existing demo/student accounts, counsellor case management, teacher assigned-case/progress-review flow, consent, notifications, daily aggregate report, and health check are unchanged.

### 7. Backout

1. Stop the new app with `Ctrl+C`.
2. Switch back to the prior release folder and its prior `.env` (or restore the original folder copy).
3. Restart the prior release using its existing `scripts\run-local.ps1`.
4. The new table is additive and can remain in the database during application rollback; do not drop it as part of routine rollback. Do not restore a database backup unless data corruption occurred and the consequences for records created after backup have been reviewed.
5. If a database restore is necessary, use the existing `scripts\restore-local.ps1` and the exact backup, after stopping the app and carefully reviewing the script's prompts.

## Operational notes

- Keep the application bound to `127.0.0.1` for local testing. Do not port-forward it or expose the laptop/database directly to the internet.
- The per-IP limiter is process-local; a public/multi-worker deployment needs a shared rate limiter at the reverse proxy or gateway.
- Use HTTPS and `COOKIE_SECURE=true` behind a properly configured reverse proxy for a shared environment.
- This is not a certification for production use with minors. Before real data, review school verification, guardian consent and student assent, privacy notice, retention, incident response, access controls, data residency/cross-border processing, and human support coverage.

## Registration retry limit

The registration endpoint permits up to **20 submissions per client IP in a rolling 15-minute window** before returning HTTP 429. This is more forgiving for students correcting school codes or invitation codes while retaining a basic abuse guard. The counter is in application memory, so it is per process and resets when the app restarts; production deployments should also apply rate limiting at the reverse proxy.
